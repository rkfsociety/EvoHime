# EvoHime — Agent Guide

EvoHime — локальный Windows AI-agent. Текущий продукт — Electron desktop application с Rust Core, SQLite и Windows supervisor.

## Общение

- Отвечай только на русском языке.
- Обращайся к пользователю «Роман».
- Используй мужской род.
- Роман не разбирается в программировании и устройстве кода; детали реализации под капотом ему не важны — главное, чтобы продукт работал так, как он просит.
- Не задавай вопросов вроде «если всё устраивает» и не перекладывай на Романа выбор технических или архитектурных решений. Самостоятельно выбирай оптимальное инженерное решение и выполняй задачу; спрашивай только при реальной неоднозначности продуктового поведения, необходимости повышения прав или перед `push`.

## Авторство изменений

- Все изменения в проекте EvoHime создаются ИИ-моделью; чужих изменений в рабочем дереве не бывает. Не классифицируй обнаруженные изменения как пользовательские или посторонние по предположению и не исключай их из работы на этом основании. Сверяй изменения с задачей и сохраняй их; разделяй по коммитам только если Роман явно просит.

## Архитектура

```text
EvoHime.exe               Electron main + bundled renderer
        │ named pipe, desktop-ipc-v1
evohime-core.exe           Rust agent runtime, tools, SQLite
        ▲
evohime-supervisor.exe    mutex, Job Object, lifecycle, recovery, logs
```

UI не обращается к workspace, SQLite или model provider напрямую. Core — единственный владелец состояния и выполнения инструментов. Supervisor запускает core, ограничивает дерево процессов Job Object и восстанавливает core после аварийного завершения.

## Требования

- Windows 10 2004+ или Windows 11, x64;
- PowerShell 7 или новее: скрипты сборки и запуска в Windows PowerShell 5.1 не
  работают и останавливаются с явной ошибкой;
- Rust MSVC toolchain;
- Node.js 22 LTS — только для разработки Electron shell; в продукт внешний
  Node.js не входит.

Electron renderer — встроенная часть desktop-приложения. Отдельный сетевой web-runtime и внешний Node.js runtime не являются частью продукта.

## IPC

Протокол редактируется в `crates/desktop-ipc/proto/evohime.desktop.proto`. Rust transport и Electron main/preload adapter должны сохранять совместимость major-версии, sequence replay и bounded frame size. Изменение протокола требует обновить обе стороны и IPC regression tests. Генерируемые TypeScript-типы проверяются `npm run check:protocol`.

Команды `workspace.*`, `chat.*`, `provider.*`, `identity.get` и `repository.get` обслуживает main-процесс: это локальное состояние оболочки, а не права. Всё, что доходит до Core, Core проверяет заново.

Подключение к Core аутентифицируется: supervisor выдаёт launch context (`%LOCALAPPDATA%/EvoHime/runtime/session.json`, owner-only DACL) с именем pipe и session secret, Core выдаёт одноразовый nonce, клиент отвечает `HMAC-SHA256(secret, role | client_id | nonce)`. Роли: `shell` (Electron), `listener` и `cli`. Общий known-answer вектор proof продублирован в Rust и Electron тестах — менять его можно только в обеих реализациях сразу.

## Данные и диагностика

- SQLite и backup: `%LOCALAPPDATA%\EvoHime` или `EVOHIME_DATA_DIR`;
- core log: `%LOCALAPPDATA%\EvoHime\logs\core.jsonl`;
- supervisor log: `%LOCALAPPDATA%\EvoHime\logs\supervisor.jsonl`;
- локальное состояние оболочки: `%LOCALAPPDATA%\EvoHime\shell\` — `workspaces.json`, `chats.json`, `provider.json`;
- обновление: `%LOCALAPPDATA%\EvoHime\update.json` (пишет установщик), `source\` — git checkout, `update-staging\` — собранный пакет, `update-state\` — журнал транзакции. В dev-запуске обновление выключено; для отладки есть `EVOHIME_UPDATE_ENABLED`, `EVOHIME_UPDATE_BRANCH`, `EVOHIME_UPDATE_SOURCE_DIR`, `EVOHIME_UPDATE_INSTALL_DIR`;
- экспорт событий — JSONL через `LocalDatabase::export_events_jsonl`.

Миграции SQLite выполняются транзакционно; перед изменением схемы создаётся backup. Секреты не попадают в исходники и логи: ключ провайдера шифруется через Electron `safeStorage` (DPAPI) в `shell\provider.json` и доходит до Core только окружением supervisor; сохранение ключа перезапускает Core. Для локальной разработки используется `.env` рядом с `start-dev.ps1` по allow-list из `.env.example`.

## Правила разработки

1. Не выноси runtime-состояние из Rust Core в Electron UI.
2. Не добавляй бизнес-логику в renderer: UI отображает состояние IPC.
3. Новые Rust-функции и исправления покрывай тестами.
   Production Rust targets во всём workspace должны запрещать
   `clippy::unwrap_used`, `clippy::expect_used` и `clippy::panic` на уровне
   crate root через `cfg_attr(not(test), deny(...))`; тестовый код сохраняет
   возможность использовать эти вызовы. Build scripts должны возвращать
   диагностируемые ошибки через `Result`. Все внешне достижимые элементы
   library API должны иметь предметные `///`-описания; полноту проверяй
   `cargo doc --workspace --lib --no-deps --locked` с `-D missing_docs`.
   Проверяй ссылки и примеры командами Rust documentation gates выше.
4. ЛОКАЛЬНО НИЧЕГО НЕ СОБИРАЕМ. Не запускай локально `cargo build`,
   `cargo test`, `cargo check`, `cargo doc`, `npm run build/package`, сборку
   пакетов, e2e и иные ресурсоёмкие команды: не нагружай устройство Романа
   без необходимости. Допустимы лёгкие проверки без компиляции
   (`git diff --check`, чтение кода, линтеры/скрипты проверки текста).
   Исключение: лёгкие тесты, не занимающие много оперативной памяти и CPU
   (узкий прогон одного crate или теста, например
   `cargo test -p <crate> <фильтр>`), можно запускать локально без отдельной
   просьбы; сначала оцени нагрузку и при заметной нагрузке остановись. Полные
   сборки и наборы тестов выполняет CI после push; запускай их локально только по
   прямой просьбе Романа. Команды выше в разделе «Команды» — справочные, а не
   разрешение запускать их по своей инициативе. В отчёте явно указывай, что
   именно запускалось локально, а что нет.
   Установка зависимостей проекта (например, `npm run bootstrap` в
   `desktop\evohime-electron` при отсутствии `node_modules` или нужных
   пакетов) под этот запрет не подпадает: установка недостающих зависимостей
   проекта обязательна и выполняется автономно, без согласования с Романом
   (кроме случаев, требующих повышения прав по правилу 5).
5. Соблюдай sandbox, таймауты, отмену и approval для опасных инструментов. Если
   команда, тест или установка требует UAC/повышенных прав (например, `os error
   740`), не обходи это ограничение: явно запроси у Романа повышение, а после
   его разрешения повтори ту же операцию и зафиксируй результат.
6. Перед заявлением о готовности проверяй `git diff --check` и итоговый diff; лёгкие тесты можно запускать локально (правило 4), остальное подтверждает CI.
7. При крупном изменении кода актуализируй соответствующую документацию: пользовательское описание, архитектуру, текущее состояние, планы, release evidence и проектные правила — по затронутой области. Не оставляй устаревшие описания действующей архитектуры.
8. После изменений создавай task-only git-коммит в текущей ветке `main`.
9. Если во время задачи или диагностики обнаружены нестыковки, расхождения или ошибки в коде, UI, тестах, CI или правилах проекта, не спрашивай разрешения — сразу исправляй их в рамках той же задачи; не оставляй такие ошибки на потом. Если задача исправляет ошибки CI текущего проекта, после task-only коммита сообщи об этом Роману и выполни push по его просьбе (правило 15), затем убедись, что нужный workflow запустился; дожидаться его завершения не обязательно — итог проверяй при следующем запросе на push. Если задача исправляет текущую проблему, воспроизводимую в установленной версии, и проверить исправление можно только после её обновления, сообщи Роману, что нужны публикация модуля и обновление установленной версии. Для остальных изменений, включая документацию и текстовые файлы, push выполняй только по прямому запросу пользователя.
10. После сборки очищай `target/`, `bin/`, `obj/` и временные package artifacts, если они больше не нужны.
11. Установленную на рабочей машине версию EvoHime разрешено запускать, останавливать и использовать для воспроизведения и диагностики ошибок, включая чтение состояния, логов и метаданных. Установленную версию нельзя исправлять: запрещены правки её кода, бинарников, конфигурации и других файлов, а также применение исправлений через installer/transaction worker, переустановку или обновление. Все исправления вносятся только в исходники; проверки исправлений выполняются на исходниках, во временных каталогах или в CI.
12. `git push` выполняй как `GIT_TERMINAL_PROMPT=0 git push origin main`: без этого флага credential manager может ждать ввода, недоступного в неинтерактивной сессии, и команда виснет до таймаута. Результат подтверждай сравнением `git ls-remote origin main` с `git rev-parse HEAD`, а не выводом самой команды — прерванный по таймауту push ничего не доказывает.
13. Если пользователь присылает ревью плана или реализации, сначала сопоставь замечания с текущим кодом и связанными документами. Обоснованные замечания исправляй сразу в рамках той же задачи, а не только пересказывай ревью; противоречивые замечания разрешай по источнику истины и явно фиксируй причину отклонения неподтверждённых замечаний. После правок проверь внутренние ссылки, зависимости, критерии готовности и согласованность с соседними этапами.
14. Не повышай версии продукта, модулей, пакетов или release-компонентов по собственной инициативе и не делай это «для запуска» workflow. Исключение: если изменены исходники публикуемого модуля и изменение должно попасть в `main`, обязательно обнови в той же задаче его `release-versions/<module>.txt`, иначе module router не увидит новую версию и не запустит пересборку/публикацию модуля. Для документационных, тестовых и CI-only изменений версии не меняй. Если пользователь не указал другой способ повышения, увеличивай только последнюю числовую часть на `+1` **относительно текущей версии в `origin/main`** (например, `1.1.0` → `1.1.1`; если локально сделано несколько коммитов поверх `origin/main`, не накручивай версию на каждый коммит — итоговая версия в `main` должна отличаться от `origin/main` ровно на `+1`, если соответствующий тег не занят); major/minor-части не меняй без явного указания. При каждом изменении исходников публикуемого модуля и/или поднятии `release-versions/<module>.txt` обязательно в том же коммите обнови в `release-notes/<module>.md` единственную секцию `## <итоговая версия>` и 1–3 коротких пункта на русском языке, понятных пользователю (без внутренних имён функций, путей, хэшей и технических терминов) — при публикации `scripts/module-release.ps1` перенесёт в `manifest.changes` и описание GitHub Release только секцию этой итоговой версии. Поэтому заметки должны описывать **всю суть реальных изменений модуля относительно версии на `origin/main`**, а не только последний локальный коммит (без раздробления на промежуточные неопубликованные секции). Первый пункт формулируй так, чтобы он укладывался в ≤ 75 символов и без скролла помещался в боковой панели окна апдейтера даже при одновременном обновлении всех модулей.
15. Push выполняй только по прямой просьбе Романа. Не запускай фоновое
   наблюдение за GitHub Actions и не опрашивай их статус самостоятельно. В
   момент, когда Роман просит пуш, проверь состояние Actions
   (`gh run list --repo rkfsociety/EvoHime --branch main --limit 10`). Если по
   `main` есть активный запуск (`queued` или `in_progress`), push запрещён даже
   по прямой просьбе: сообщи Роману, какой именно запуск мешает, и не пушь до
   его завершения. Исключение — зависший `queued`: запуск, созданный больше трёх
   часов назад и всё ещё стоящий в очереди, блокером не считается, потому что
   после сбоя GitHub такая запись может остаться навсегда, а отменить её
   штатными средствами нельзя; перечисли такие запуски в ответе перед пушем.
   Тогда же проверь последний завершённый запуск каждого workflow по `main`,
   а не только последний запуск в общем списке. Если последний запуск любого
   workflow завершился `failure` или `startup_failure`, открой его логи,
   установи и исправь причину до push, выполни доступную локальную проверку и
   включи исправление в task-only коммит. Если тот же workflow уже имеет более
   новый успешный запуск, старое падение не блокирует push. Если нового
   успешного запуска ещё нет, после исправления и прямого запроса Романа
   выполни push и убедись, что соответствующий workflow стартовал; дожидаться
   завершения не требуется. Один только отчёт о падении вместо исправления и
   push по запросу недопустимы.
16. В момент пуша, помимо проверки Actions, сверяй релизные версии: для
    каждого публикуемого модуля, чьи исходники изменены уходящими коммитами,
    проверь, что его маркер `release-versions/<module>.txt` поднят относительно
    `origin/main` (последняя числовая часть увеличена на `+1`, см. правило 14),
    и что тега `module-<module>-v<новая версия>` ещё нет в origin. Если маркер
    не поднят — не пушь, подними версию в той же задаче; если тег уже существует,
    новая сборка не запустится — подними маркер ещё на шаг. Документационные,
    тестовые и CI-only изменения версий не требуют — фиксируй это в ответе
    перед пушем.
17. Модули `evohime-core` и `evohime-hive` полностью разделены: `evohime-core` не
    имеет права зависеть от `evohime-hive` в `Cargo.toml` или содержать
    бизнес-логику/реконсиляцию Улья. Единственная общая точка — минимальный
    контракт `evohime-hive-contract`. Изменения внутри `crates/evohime-hive/**` не
    должны требовать правок в `crates/evohime-core/**` или поднятия
    `release-versions/core.txt`.

## Документы

- `docs/README.md` — карта документации и правило источника истины;
- `docs/architecture.md` — канонический остов архитектуры (границы, процессы, IPC, инварианты, карта); доменные контракты — в `docs/architecture/*.md`;
- `docs/current-state.md` — подтверждённое состояние checkout;
- `docs/development-plan.md` — актуальный implementation plan;
- `docs/roadmap.md` — долгосрочные направления без деталей реализации;
- `docs/features/`, `docs/providers/`, `docs/security/` — справочные разделы;

Все планы лежат в `docs/plans/`; порядок и правило нумерации описаны в `docs/plans/README.md`. Один файл — один этап (`NN-M-slug.md`, где `M = 0` — обзор плана), поэтому этап ревьюется и выпускается отдельно. Новый план получает следующий свободный номер и обязан разделить зависимости на блокирующие и опциональные. Блокирующая зависимость от более позднего этапа означает, что номера расставлены неверно. Реализованный план удаляется из каталога: его контракт переезжает в доменный файл `docs/architecture/` (один домен — один файл; новый домен — новый файл); `docs/architecture.md` хранит только границы, процессы, инварианты и карту и меняется лишь при их изменении, а состояние — в `docs/current-state.md`. Лимиты: `docs/architecture.md` ≤ 500 строк, доменный файл `docs/architecture/*.md` ≤ 2000 строк.
