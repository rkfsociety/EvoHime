# Backup restore: import сессий и памяти

## Цель

Вторая волна `7.99`: превратить переносимый `BackupDump` в реально переносимый — добавить идемпотентный импорт дампа в PostgreSQL, чтобы push-копию (`7.99` wave 1) или файл `evohime-export` (`7.97`) можно было развернуть на другой машине.

## Выбранный подход

Импорт реализуется как функция storage `restore_backup(pool, operator_id, dump)` и CLI `evohime-import` — зеркально к `evohime-export`. Remote pull через API не вводится в этой волне: скачивание файла с приёмника — тривиальная операция вне ядра, а вот корректная вставка связанных сущностей — то, что должно жить рядом со схемой.

Импорт идемпотентен на уровне **сессий и memory items**:

- сессия с существующим `id` пропускается целиком вместе со своими messages/tasks/steps/events — это исключает дубли `session_messages`, у которых нет переносимого id;
- memory item с существующим `id` пропускается;
- повторный запуск на той же базе ничего не добавляет.

Все восстановленные строки получают `operator_id` целевого оператора, а не значения из дампа: дамп по построению принадлежит одному оператору, а восстановление может выполняться под другим (миграция на новую машину с новым registry).

## Обработка ссылок

- `memory_items.source_session_id` / `source_task_id`: сохраняются, только если целевая строка существует после вставки сессий; иначе `NULL` (семантика `ON DELETE SET NULL` уже допускает потерю источника).
- `memory_items.supersedes`: восстанавливается вторым проходом после вставки всех items, только для существующих целей.
- `embedding`/`embedding_version` переносятся как есть; повторное кодирование не требуется.

## Атомарность и ошибки

- Весь импорт выполняется в одной транзакции: сбой любой вставки откатывает всё, частично восстановленной базы не остаётся.
- Дамп с неизвестным `format` или `version` отклоняется до начала транзакции.
- Целевой оператор должен существовать и быть активным.
- CLI не выводит содержимое дампа; отчёт содержит только счётчики.

## CLI

`evohime-import --input <path> [--operator-name <name>]`

- `--input` — путь к JSON-дампу; файл читается целиком и валидируется.
- `--operator-name` — имя целевого оператора из registry; по умолчанию bootstrap `local-owner`.
- Выход: отчёт `inserted/skipped` по сессиям и memory items, счётчики messages/tasks/steps/events; ненулевой код при любой ошибке.

## Реализационные границы

Вне волны: remote pull endpoint (`GET` с приёмника + импорт по API), merge-стратегии при конфликте содержимого (сейчас — skip by id), восстановление worker jobs/sites/scheduled. Всё это ложится поверх того же `restore_backup`.

## Проверка

- unit-тесты: валидация формата/версии, отчёт;
- storage integration-тесты: round-trip export → import в чистого оператора (всё вставлено), повторный import (всё пропущено), сохранение и NULL-инг ссылок memory;
- CLI smoke: импорт файла, ошибка на битом JSON;
- полный Rust workspace test, Clippy, frontend build.

## Критерий готовности

`evohime-export` на машине A и `evohime-import` на машине B переносят сессии (messages/tasks/steps/events) и memory items под указанного оператора; повторный запуск import ничего не дублирует; сбой посреди импорта не оставляет частичных данных.
