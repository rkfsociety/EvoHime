# Cloud sync: автоматический push по расписанию

## Цель

Финальная волна `7.99`: off-machine копия обновляется сама. Сервер периодически выполняет тот же push, что и `POST /api/sync/push`, без участия оператора — деплой с настроенным remote получает свежий backup без ручных вызовов.

## Выбранный подход

Фоновый tokio-цикл в server-процессе (по образцу `scheduler_loop` и `metrics_persist_loop`), а не отдельный cron-механизм: авто-sync — это инфраструктурная задача деплоя, ей не нужны session/task-обвязка scheduled tasks и UI управления.

Цикл переиспользует push-движок wave 1 целиком: сбор дампа, checksum, `PUT`, запись run в `sync_runs`. Ручной push и авто-push неразличимы для приёмника и истории; отличается только инициатор.

Авто-push выполняется для **bootstrap local owner** — той же identity, что использует `evohime-export` и legacy `EVOHIME_API_TOKEN`. Per-operator авто-sync сознательно не вводится: один `EVOHIME_SYNC_URL` — одна цель `PUT`, дампы разных операторов перезаписывали бы друг друга; namespacing приёмника — отдельная будущая работа.

## Конфигурация

- `EVOHIME_SYNC_AUTO_MINUTES` — период в минутах; `0`/не задан → авто-sync выключен. Значения меньше 5 поднимаются до 5, чтобы деплой не мог заDDoSить приёмник конфиг-опечаткой.
- Работает только при заданном `EVOHIME_SYNC_URL` и включённом `EVOHIME_FEATURE_CLOUD_SYNC`; иначе тик пропускается без ошибки.
- `GET /api/sync/status` дополняется полем `auto_minutes` (`null` — выключен).

## Поведение и ошибки

- Тик пропускается, если у owner уже есть активный run (ручной push/pull в процессе): авто-sync никогда не конкурирует с оператором.
- Ошибка push (remote недоступен, конфиг сломан) логируется и фиксируется как failed run; цикл продолжает работать — авто-sync не может уронить сервер.
- Первый push выполняется через полный интервал после старта, не мгновенно: рестарт сервера не порождает шторм push при цикличных перезапусках.
- Токен по-прежнему нигде не логируется; сообщения цикла содержат только run id, статус и размер.

## Реализационные границы

Вне волны: per-operator авто-sync и namespacing на приёмнике, авто-pull (двусторонняя синхронизация требует разрешения конфликтов и не должна происходить без оператора), UI-панель синхронизации.

## Проверка

- unit-тесты разбора/клампа интервала;
- существующие push-тесты покрывают движок; цикл — тонкая обвязка;
- полный Rust workspace test, Clippy, регенерация OpenAPI при изменении status-формы, frontend build.

## Критерий готовности

Деплой с `EVOHIME_SYNC_URL` и `EVOHIME_SYNC_AUTO_MINUTES=30` каждые 30 минут создаёт push run в `sync_runs` без участия оператора; при недоступном remote появляются failed runs, сервер живёт; `GET /api/sync/status` показывает `auto_minutes: 30`; при `0`/отсутствии переменной поведение идентично wave 1–3.
