# Cloud sync: push операторского backup

## Цель

Начать `7.99` (cloud sync / remote workspace) с честной первой вертикали: сервер по запросу владельца отправляет переносимый backup своих данных на настроенный удалённый endpoint и хранит историю попыток. Это даёт off-machine копию данных без внешнего SaaS и без изменения локального рантайма.

## Выбранный подход

Первая волна — **push-only** синхронизация существующего `BackupDump` (`7.97`) по HTTP. Собственный протокол репликации, S3-клиент и pull/restore не вводятся: дамп уже переносим, а любой HTTP-приёмник (второй EvoHime, object-storage gateway, простой WebDAV/ingest сервис) может принять `PUT` с JSON-телом. Это минимальная поверхность, которая не фиксирует преждевременно формат будущей двусторонней синхронизации.

Remote endpoint задаётся оператором развёртывания через env, а не через пользовательский ввод: URL — доверенная конфигурация, аналогично OTLP endpoint. Пользовательский запрос не может подменить адрес назначения.

## Конфигурация

- `EVOHIME_SYNC_URL` — базовый endpoint (только `http`/`https`). Не задан → sync «не сконфигурирован», push возвращает понятную ошибку.
- `EVOHIME_SYNC_TOKEN` — опциональный bearer для удалённого приёмника.
- `EVOHIME_FEATURE_CLOUD_SYNC` — experimental flag (default enabled, как остальные), отражается в `/api/features`; при отключении sync endpoints возвращают 404-эквивалент через feature gate.

## Модель данных

Миграция `0026_sync_runs.sql` добавляет `sync_runs`:

- `id`, `operator_id` (FK на `operators`), `started_at`, `finished_at`;
- `status` (`running` / `success` / `failed`);
- `bytes_total`, `checksum` (SHA-256 дампа), `error`;
- индекс по `(operator_id, started_at DESC)`.

История строк — источник статуса «когда последний раз удался push». Токены и полный URL в таблице не хранятся.

## API первой волны

Owner-only endpoints (member получает `403`):

- `GET /api/sync/status` — `configured`, host назначения без credentials, последние runs;
- `POST /api/sync/push` — собрать `BackupDump` текущего оператора, сериализовать, посчитать SHA-256, выполнить `PUT` на remote и записать run.

`PUT` уходит с `Content-Type: application/json` и заголовком `X-EvoHime-Backup-Checksum`. Ответ 2xx — успех; иное — failed run с усечённым описанием ошибки.

## Безопасность и ошибки

- URL валидируется: только `http`/`https`, без userinfo в URL.
- HTTP-клиент не следует redirect (иначе bearer может утечь на другой host) и имеет таймаут.
- Токен не попадает в логи, ошибки, `/api/sync/status` и таблицу runs.
- Тело ответа удалённой стороны не сохраняется и не логируется целиком; ошибка усечена по длине.
- Одновременно допускается один активный push на оператора: при наличии свежего `running` run возвращается `409`.
- `running` run старше порога считается брошенным (после рестарта сервера) и не блокирует новый push.
- Push не изменяет локальные данные; сбой remote не влияет на рантайм.

## Реализационные границы

Вне первой волны: pull/restore на другой машине, автоматический sync по расписанию, инкрементальные дампы, S3-протокол, выбор endpoint через UI и UI-панель синхронизации. Всё это подключается поверх той же `sync_runs`-истории и конфигурации отдельными изменениями.

## Проверка

- unit-тесты: валидация URL, редакция host для status, checksum, разбор конфигурации;
- storage integration-тесты: запись/завершение/выборка runs, изоляция операторов;
- HTTP-тесты: `403` для member, ошибка при отсутствии конфигурации;
- полный Rust workspace test, Clippy, регенерация OpenAPI и frontend typecheck/build.

## Критерий готовности

При заданном `EVOHIME_SYNC_URL` владелец вызывает `POST /api/sync/push`, дамп уходит `PUT`-запросом с checksum-заголовком, run фиксируется как `success` с размером и checksum; при недоступном remote run фиксируется как `failed` с безопасным сообщением; `GET /api/sync/status` показывает конфигурацию и историю без секретов; member получает `403`.
