# Continual learning: обучение на проваленных задачах

## Цель

Начать `7.103` (online continual learning без fine-tune): сейчас после провала задачи память не обновляется вообще (`if !task_ok { return; }`) — система наступает на те же грабли бесконечно. Волна добавляет **ограниченную полосу** извлечения опыта из провалов: только `failure_pattern` и `verification_rule`, только scope `experience`, только через подтверждение оператора.

## Пересмотр старого решения

Пропуск провалов был осознанным (защита от ask-спама и мусорных «фактов» из сломанных прогонов). Волна не отменяет мотив, а сужает канал:

- из провала **нельзя** извлечь fact/preference/constraint/success_pattern/playbook — сломанный прогон не источник истины о мире;
- можно извлечь максимум **2** кандидата за провал: «что пошло не так» (`failure_pattern`) и «что проверять заранее» (`verification_rule`);
- confidence кандидатов принудительно капится **ниже** `AUTO_PROMOTE_CONFIDENCE` (0.7 → cap 0.6): auto-promote невозможен by construction, каждый кандидат идёт через существующий Ask-гейт. Оператор решает, что из провала стало уроком.

Провал — это сигнал, а два вопроса после реально проваленной задачи — не спам.

## Реализация

- `crates/memory`: `extract_failure_candidates(llm_raw)` — parse существующим `parse_extraction_json`, затем retain только `(Experience, FailurePattern | VerificationRule)`, cap confidence 0.6 / importance 0.7, существующие transient/ephemeral фильтры, лимит 2. Эвристического fallback нет: нет LLM-вывода — нет кандидатов.
- `crates/server/task/memory.rs`: отдельный `FAILURE_EXTRACT_PROMPT` (анализ провала: симптом, вероятная причина, что проверять) и ветка в `persist_structured_memory` для `!task_ok`, использующая тот же admit/gate/event-конвейер.
- Существующая фидбек-петля (`harmful` для использованной памяти при провале) не меняется — она уже работает.

## Поведение и ошибки

- LLM-extract с таймаутом (существующий механизм); таймаут/мусор → ноль кандидатов, никакого фолбэка на транскрипт.
- Транзиентные инфраструктурные ошибки (`is_transient_infra_failure`) отфильтровываются — обрыв сети не «урок».
- Дедуп/конфликт — существующий admit-сервис; повторный провал с тем же паттерном не плодит дубликаты.

## Реализационные границы

Вне волны: автоматическая эскалация confidence при повторении паттерна, retrieval-приоритизация failure_patterns перед похожими задачами (retrieve уже включает experience), периодическая консолидация уроков. Всё ложится поверх той же полосы.

## Проверка

- unit-тесты: retain-фильтр (fact из провала отброшен, failure_pattern оставлен), кап confidence/importance, лимит 2, пустой/мусорный вывод → пусто;
- проверка гейта: кандидат с capped confidence получает `Ask`, не `AutoPromote`;
- полный Rust workspace test, Clippy, frontend build.

## Критерий готовности

После проваленной задачи в Memory-панели появляется до двух Ask-кандидатов (`failure_pattern`/`verification_rule`, scope experience); никакие fact/preference из провала не создаются; auto-promote из провала невозможен; успешные задачи ведут себя как раньше.
