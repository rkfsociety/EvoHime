# EvoHime Shell Design

## Цель

Сделать полноценную нативную оболочку Евы, в которой уже на первом экране можно открывать workspace, создавать диалог, вставлять тестовые данные, наблюдать состояние агента и постепенно подключать реальные функции Core.

Оболочка должна быть узнаваемой как рабочее пространство coding-agent приложения, но не копировать внешний вид или брендинг других продуктов.

## Пользовательский сценарий

1. Пользователь запускает `EvoHime.exe` и видит рабочее пространство Евы.
2. В левой навигации выбирает новый чат, проект, задачу или системный раздел.
3. В центре открывается текущая рабочая область: приветствие/empty-state, сообщения, поле ввода и поток событий.
4. В верхней панели пользователь открывает компактную сводку workspace.
5. Сводку можно оставить popover-окном или закрепить как узкий виджет поверх правой части рабочей области.
6. Пользователь может выбрать workspace и отправить тестовую задачу через существующий native IPC.
7. Ненастроенные функции показывают честное состояние раздела, а не декоративную кнопку без результата.

## Визуальное направление

- Основной стиль: тёмная «ночная мастерская».
- Основа: графитовый фон, мягкие поверхности, тонкие разделители.
- Акценты: собственная комбинация фиолетового и бирюзового, используемая для активных элементов, статусов и прогресса.
- Плотность: компактная, но с достаточными отступами для Windows desktop и мыши/клавиатуры.
- Состояния: idle, hover, active, disabled, running, success, warning и error должны различаться цветом и текстом.
- Никаких чужих логотипов, названий, скриншотных копий или прямого переноса палитры.

## Компоновка

### Левая навигация

Широкая фиксированная область содержит:

- верхнюю строку с именем `Ева`, поиском и уведомлениями;
- `Новый чат`;
- `Пульс` — активность задач, Core и фоновых процессов;
- `Запланировано`;
- `Плагины`;
- список проектов/workspace;
- последние диалоги;
- нижний блок профиля, настроек и экспорта диагностики.

Список проектов должен поддерживать выбор текущего workspace и понятное состояние, если путь ещё не выбран.

### Центральная рабочая область

Центр является главным экраном:

- заголовок текущего проекта/диалога;
- приветственный или пустой экран без фиктивных данных;
- история сообщений Евы и пользователя;
- поле задачи с поддержкой многострочного ввода;
- отправка, Stop и состояние текущего выполнения;
- поток native событий и approval-запросов;
- inline-состояния ошибки, переподключения и восстановления.

UI только отображает state reducer и отправляет команды через IPC. Работа с файлами, shell, Git, Core и SQLite остаётся за native Core.

### Верхняя панель и виджет сводки

В верхней панели находятся компактные кнопки вида и состояния. Кнопка workspace открывает сводку поверх рабочей области.

Сводка содержит:

- изменения workspace и краткую статистику строк;
- текущий локальный workspace;
- Git-ветку;
- действия commit/send и сравнения ветки;
- фоновые процессы;
- источники и подключения.

По умолчанию сводка является узким popover. Пользователь может закрепить её, после чего она остаётся узким виджетом и не превращается в широкую панель. Закрытие popover выполняется повторным кликом, Escape или кликом вне окна.

## Состояния разделов

Каждый раздел первой оболочки имеет настоящий экран и одно из состояний:

- `Ready` — данные доступны;
- `Empty` — данных пока нет, показано действие настройки;
- `Loading` — идёт запрос через IPC;
- `Running` — выполняется задача или процесс;
- `Degraded` — Core/IPC временно недоступен;
- `Error` — показана безопасная ошибка и действие восстановления.

Разделы, чьи backend-функции ещё не подключены, используют объяснимый empty-state с дальнейшим действием. Они не должны имитировать завершённую функциональность.

## Архитектура

- `EvoHime.Desktop` отвечает за навигацию, визуальное состояние, фокус, хоткеи, popover/виджет сводки и native dialogs.
- `TaskStateReducer` и отдельные state-модели преобразуют IPC-события в UI state, игнорируя устаревшие и повторные sequence IDs.
- `CoreIpcClient` остаётся единственным каналом команд и событий между UI и Core.
- Rust Core владеет workspace, задачами, файлами, Git, terminal, approvals, памятью и SQLite.
- Стили и размеры должны быть вынесены в общий ресурсный слой WinUI, чтобы позднее менять внешний вид без переписывания экранов.
- Новые экраны добавляются как независимые views/components, а не разрастающимся `MainWindow`.

## Первый набор экранов

1. Новый чат / рабочее пространство.
2. Пульс — задачи, события, состояние supervisor/Core.
3. Проекты — список workspace и выбор текущего пути.
4. Запланировано — empty-state с подготовленным контейнером будущих задач.
5. Плагины — empty-state и список подключённых источников, когда Core начнёт их отдавать.
6. Настройки — тема, workspace по умолчанию, обновления и диагностика.

Files, Editor, Git и Terminal подключаются в эту оболочку после стабилизации навигации и состояния, но их контракты не должны ломать первый экран.

## Тестирование и критерии готовности

- UI smoke запускает native EXE и подтверждает, что главное окно остаётся живым.
- Навигационные тесты проверяют каждый раздел, переход назад и сохранение выбранного workspace.
- Reducer-тесты проверяют порядок событий, duplicate/stale sequence IDs, task lifecycle, reconnect и approval.
- Popover-тесты проверяют открытие, Escape, клик вне окна, pin/unpin и сохранение узкой ширины виджета.
- Empty/loading/degraded/error состояния проверяются без реального внешнего сервиса.
- WinUI CI build, IPC compatibility tests и package smoke остаются обязательными до release build.
- Установленная версия пользователя не используется как диагностический стенд; проверка выполняется на отдельной staging-сборке.

## Границы первой итерации

В первую итерацию входят оболочка, навигация, пустые/загрузочные состояния, workspace selector, чатовый контейнер, сводка и подключение к существующим IPC-событиям. Полный файловый редактор, Git-операции, controlled Terminal, плагины и расписание реализуются отдельными итерациями внутри той же оболочки.
