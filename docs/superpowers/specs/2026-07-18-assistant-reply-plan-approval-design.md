# Assistant Reply и подтверждение плана — дизайн

## Цель

Реализовать Stage 7.35: перед выполнением инструментов показывать пользователю план агента, позволять отредактировать шаги и запускать только утверждённую версию.

## Решение

План хранится в существующем PostgreSQL `task_checkpoints.state_json`. После первой генерации плана сервер сохраняет его, переводит задачу в `paused` с причиной `plan_approval_required` и публикует план. Новая команда `task.plan.approve` принимает полный отредактированный массив шагов, валидирует его, заменяет checkpoint и возобновляет pipeline. Команда `task.plan.reject` отменяет ожидающую задачу.

Утверждение должно переживать переподключение браузера и рестарт сервера: состояние восстанавливается из checkpoint, а повторное approve допускается только для задачи со статусом `paused` и соответствующей причиной.

## Поток данных

```text
LLM plan → persist checkpoint → paused(plan_approval_required)
         → agent.plan.updated + task.status.changed
Browser edit → task.plan.approve(plan)
             → validate → replace checkpoint/task_steps → resume pipeline
```

UI использует текущие `Tasks`/плановые события, но добавляет редактор описаний, инструмента и зависимостей. Отмена плана оставляет задачу отменённой и не запускает инструменты.

## Валидация и ошибки

- план не пустой и содержит не более существующего лимита шагов;
- id шагов уникальны, `tool_name` не пустой;
- зависимости ссылаются только на существующие шаги и не образуют цикл;
- approve/reject для другой сессии или не ожидающей задачи игнорируется с `ActionLogged`;
- ошибка валидации не меняет checkpoint и возвращается через структурированный action detail.

## Тестирование

Rust-тесты покрывают сериализацию новых команд, валидацию плана и переход состояния ожидания. Frontend-тесты покрывают отображение редактора, отправку approve/reject и сохранение плана после server event. После этого запускаются `cargo test --workspace` и `npm run build` из `frontend/web`.
