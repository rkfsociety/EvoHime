# Eval harness: golden tasks

## Цель

Начать `7.101`: регрессионная защита поведения агента. Golden task фиксирует сценарий «сообщение пользователя → детерминированный сценарий модели → реальные инструменты → проверяемый результат»; изменение agent loop, парсинга tool calls или инструментов, ломающее сценарий, падает в CI, а не у пользователя.

## Выбранный подход

Новый workspace-крейт `crates/evals` (`evohime-evals`). Harness запускает **настоящий** `run_agent_loop` с **настоящим** `ToolRegistry::bootstrap()` во временном workspace; недетерминированна только модель — она заменяется `MockProvider::with_tool_call_sequence`, проигрывающим сценарий задачи. Это осознанная граница: eval проверяет всё, что контролирует EvoHime (loop, парсинг, инструменты, sandbox), и не проверяет качество LLM, которое EvoHime не контролирует.

Golden tasks — JSON-файлы в `crates/evals/golden/`. Раннер — интеграционный тест крейта: `cargo test --workspace` в CI выполняет все golden tasks без отдельного job (регрессионные агенты «бесплатно» на каждом push). Дополнительно bin `evohime-eval` печатает пофайловый отчёт локально и возвращает ненулевой код при провале.

## Формат golden task

```json
{
  "name": "write-then-confirm",
  "user_message": "Создай hello.txt",
  "workspace_files": { "seed.txt": "seed" },
  "script": [
    { "tool": "filesystem.write", "input": { "path": "hello.txt", "content": "hi" } },
    { "reply": "Готово" }
  ],
  "expect": {
    "final_message_contains": ["Готово"],
    "files": [ { "path": "hello.txt", "contains": "hi" } ]
  }
}
```

- `script` — последовательность ответов модели: шаг `tool` превращается в native tool call, шаг `reply` — в финальный текст;
- `workspace_files` — seed временного workspace;
- `expect` — подстроки финального сообщения и файлы (существование + подстрока содержимого).

## Поведение и ошибки

- Каждая задача изолирована: свой temp workspace, свой mock-провайдер; порядок задач не влияет на результат.
- Провал ожидания даёт diagnostic со списком именно нарушенных ожиданий, а не общий assert.
- Невалидный JSON задачи — это провал раннера с именем файла, не тихий пропуск.
- Harness не обращается к сети и PostgreSQL (`memory_pool: None`); никакого реального LLM.

## Реализационные границы

Вне волны: скоринг похожести ответов (LLM-as-judge), сравнение с живыми провайдерами, панель результатов в UI, benchmark производительности. Формат рассчитан на расширение полей `expect` без ломки существующих задач.

## Проверка

- unit-тесты: парсинг формата, конвертация script → ChatResult, проверка ожиданий (позитив/негатив);
- интеграционный тест: все golden tasks из каталога проходят; первая волна включает минимум три задачи — reply-only, чтение файла, запись файла;
- полный Rust workspace test (включая новый крейт), Clippy, frontend build; CI покрывает крейт существующими `--workspace` jobs.

## Критерий готовности

`cargo test -p evohime-evals` прогоняет все golden tasks против реального agent loop с mock-моделью; поломка формата ответа agent loop или инструмента ломает тест с внятным сообщением; `cargo run -p evohime-evals --bin evohime-eval` печатает отчёт по задачам и возвращает ненулевой код при провале.
