# План развития Евы по мотивам opencode.nvim

## Цель

Перенести в native WinUI/Rust-архитектуру EvoHime наиболее полезные идеи из `sudo-tee/opencode.nvim`: полноценный контекст запроса, разделение безопасного планирования и выполнения, устойчивые сессии, просмотр изменений и восстановление состояния.

Сам `opencode.nvim` не подключается как готовый модуль: он является Lua-плагином для Neovim и работает через отдельный `opencode` CLI. В EvoHime используются только совместимые продуктовые идеи.

## Принципы

- UI только отображает состояние и отправляет команды через versioned named-pipe IPC.
- Core остаётся владельцем сессий, контекста, snapshots, разрешений и состояния задач.
- Любой новый IPC message обновляет Rust и C# стороны одновременно и получает compatibility-тест.
- Изменения файлов выполняются только после подтверждения и должны быть видны в diff.
- Режим планирования не должен иметь права записи, запуска shell и создания commit.
- Секреты, содержимое ключей и чувствительный контекст не попадают в trace без явного разрешения.

## Этап 1. Режимы «План» и «Сборка»

### Что сделать

1. Добавить в composer переключатель режима:
   - `План` — исследование, чтение, поиск, анализ и отчёт;
   - `Сборка` — изменение файлов, тесты, commit и запросы approval.
2. Передавать выбранный режим в `TaskCommand` через IPC.
3. В Core связать режим с allowlist инструментов:
   - `План`: filesystem read/search, git status/diff, безопасная диагностика;
   - `Сборка`: полный набор после approval.
4. Отображать режим в trace и карточке текущей задачи.
5. При попытке запрещённого инструмента возвращать понятное событие, а не молча завершать задачу.

### Проверка

- План не может изменить файл, запустить shell или создать commit.
- Сборка продолжает работать с текущими approval и delivery-gate.
- Старые IPC-клиенты сохраняют совместимость с режимом по умолчанию `build`.

## Этап 2. Управляемый контекст запроса

### Что сделать

1. Ввести сущность `ContextItem` с типами:
   - текущий файл;
   - выбранные файлы;
   - выделенный фрагмент;
   - диагностика;
   - позиция курсора;
   - вложение.
2. Добавить в UI панель контекста над composer:
   - список элементов;
   - удаление элемента;
   - очистка контекста;
   - размер каждого элемента.
3. Добавить file picker и быстрый ввод `@path` для добавления файлов.
4. Перед отправкой формировать контекст в Core, а не собирать бизнес-логику в UI.
5. Реализовать delta-поведение: неизменившийся файл не отправляется повторно в рамках сессии.
6. Ограничить размер контекста и показывать предупреждение до отправки.

### Проверка

- Модель получает ровно выбранные файлы и выделения с workspace-relative путями.
- Повторная отправка неизменившегося файла не дублирует его содержимое.
- Пути за пределами workspace отклоняются.
- Секретные файлы и `.git` исключаются по правилам безопасности.

## Этап 3. Постоянные сессии и история

### Что сделать

1. Перенести историю сообщений из временного UI-состояния в Core/SQLite.
2. Расширить chat/session модель:
   - `session_id`, название, проект, режим, модель;
   - сообщения пользователя и Евы;
   - tool events и итог задачи;
   - время создания/обновления;
   - архивный статус.
3. Добавить в sidebar:
   - выбор сессии;
   - переименование;
   - архивирование;
   - удаление с подтверждением;
   - продолжение последней сессии.
4. Добавить timeline последнего запуска с возможностью открыть trace конкретного шага.
5. Подготовить миграцию SQLite и backup перед изменением схемы.

### Проверка

- Перезапуск UI не теряет диалог.
- Сессии разных проектов не смешиваются.
- Архивная сессия не появляется среди активных.
- Повторное открытие показывает сообщения, trace и итог задачи.

## Этап 4. Diff, snapshots и восстановление

### Что сделать

1. Перед первым изменением задачи создавать snapshot workspace средствами Core.
2. После каждого успешного шага изменения сохранять набор затронутых файлов.
3. Добавить экран `Изменения`:
   - список файлов;
   - unified diff;
   - просмотр добавленных/удалённых строк;
   - переход к файлу.
4. Добавить действия:
   - откатить файл последнего шага;
   - откатить все изменения последнего запроса;
   - восстановить snapshot задачи;
   - открыть текущий diff в Git.
5. Все операции восстановления делать только через Core и журналировать в trace.

### Проверка

- Откат одного файла не затрагивает остальные.
- Восстановление snapshot возвращает состояние до задачи.
- Незакоммиченные пользовательские изменения не затираются без явного approval.
- После восстановления UI обновляет project/chat state.

## Этап 5. Улучшение composer и вывода

### Что сделать

1. Добавить историю введённых запросов с клавишами вверх/вниз.
2. Добавить slash-команды для безопасных действий:
   - `/context`;
   - `/diff`;
   - `/status`;
   - `/plan`;
   - `/build`;
   - `/compact`.
3. Добавить переключение модели и варианта модели прямо из composer.
4. В trace сделать сворачиваемые блоки tool output и raw model output.
5. Добавить отдельный просмотр полного сырого события для диагностики.
6. Сохранить текущие функции копирования сообщения, всего чата и trace.

### Проверка

- Enter продолжает отправлять запрос, а Shift+Enter добавляет новую строку.
- Slash-команды не отправляются модели как обычный текст.
- Длинный trace не блокирует UI и не раздувает визуальную область.

## Этап 6. Дочерние задачи и компактирование

### Что сделать

1. Разрешить Core создавать дочернюю read-only сессию для исследования.
2. Показать связь parent/child в timeline.
3. Запретить изменения из read-only дочерней сессии.
4. Добавить ручное и автоматическое compact-событие при приближении к лимиту контекста.
5. Перед compact сохранять полный trace и ссылку на исходную историю.

### Проверка

- Child session не может вызвать write/shell/commit.
- Compact сохраняет смысл задачи и список активного контекста.
- После compact можно продолжить исходную сессию.

## Порядок реализации

1. Режимы `План/Сборка` и IPC allowlist.
2. Контекст запроса и file mentions.
3. Сохранение сообщений и полноценные сессии.
4. Snapshots и diff/rollback.
5. История prompt, slash-команды и улучшение trace.
6. Дочерние сессии и compact.

Каждый этап должен быть отдельным task-only commit с Rust-тестами, WinUI-тестами, `git diff --check` и проверкой запуска native-пакета.

## Критерии готовности всего плана

- Ева может работать в режиме анализа без риска изменения workspace.
- Пользователь управляет точным контекстом запроса и видит его размер.
- Диалоги и trace сохраняются между перезапусками.
- Каждое изменение можно увидеть и безопасно откатить.
- UI остаётся thin client, а Core сохраняет владение состоянием и инструментами.
