# Ручное тестирование «Улья» (Hive / EvaPulse)

Эта инструкция предназначена для ручной проверки установленного Windows-клиента
EvoHime. Проверяйте Улей на отдельном тестовом проекте и не используйте для этой
проверки реальные секреты, если они не нужны.

> **Важно.** `eva_workspace_path` — это отдельный существующий Git checkout
> исходников EvoHime. Он не должен совпадать с каталогом установленного клиента,
> запущенным workspace или одним из обычных рабочих каталогов. Пути должны быть
> доступны текущему пользователю Windows.

## 1. Подготовка

### 1.1. Обновить установленную версию EvoHime

1. Закройте окно EvoHime и дождитесь завершения текущих задач.
2. Запустите установленный `EvoHime-Setup.exe` из официального релиза проекта.
   Это тот же updater, который используется для первой установки и восстановления
   клиента.
3. Дождитесь проверки манифеста, скачивания модулей и health-check. Не закрывайте
   updater во время обновления.
4. Запустите EvoHime через обычный ярлык и убедитесь, что приложение подключилось
   к Core. Пользовательские данные в `%LOCALAPPDATA%\EvoHime` при обновлении не
   удаляются.

### 1.2. Открыть настройки Улья

1. Откройте вкладку **«Улей»** в EvoHime.
2. Нажмите значок **шестерёнки** в панели Улья.
3. Должно открыться окно **«Настройки улья»**. Если Core ещё не подключён,
   сначала дождитесь состояния подключения.

### 1.3. Добавить наблюдаемый проект

1. В разделе **«Проекты Улья (watched_repositories)»** вставьте путь к
   существующему Git-репозиторию, например `C:\Projects\hive-test`.
2. Нажмите **«Добавить проект»**.
3. Проверьте, что путь появился в списке. Для теста используйте проект, в котором
   можно безопасно создать временную Markdown-задачу.
4. Убедитесь, что в списке нет `eva_workspace_path`: исходники Евы сканируются
   отдельно и не должны дублироваться в списке внешних проектов.

### 1.4. Указать `eva_workspace_path`

1. В поле **«Путь к исходникам Евы (eva_workspace_path)»** укажите отдельный
   checkout EvoHime, например `C:\EvoHime-self-development`.
2. Нажмите **«Проверить»**. Ожидается отметка о валидном Git-репозитории.
3. Нажмите **«Сохранить»**.
4. В настройках должен появиться признак включённого Улья, а подсказка должна
   сообщить, что инструменты `eva_workspace_*` доступны Королеве.

Если проверка отклонена, проверьте, что каталог существует, содержит `.git`, не
является установленным продуктом и не совпадает с активным workspace.

### 1.5. Настроить отдельный API-ключ Улья

1. В настройках Улья выберите основной **«Провайдер Улья»** и модель, затем
   нажмите **«Сохранить провайдер Улья»**.
2. В поле **«API-ключ Улья»** введите ключ выбранного провайдера и нажмите
   **«Сохранить ключ»**.
3. При необходимости выберите **«Резервный провайдер Улья»**, модель и сохраните
   отдельный **«Резервный API-ключ Улья»**.
4. Убедитесь, что появилось подтверждение сохранения. Ключ вводится только в
   поле `type=password`: он хранится оболочкой в зашифрованном хранилище и не
   должен появляться в snapshot, journal или логах.

Для недорогого теста выберите бесплатный режим LiteRouter (`:free`), если он
доступен. Без настроенного основного маршрута EvaPulse остаётся в состоянии
ожидания и фоновые задачи не запускает.

## 2. Проверка UI (дашборд)

После открытия вкладки **«Улей»** подождите обновления снимка состояния. Не
считайте обычный чат источником данных Улья: Улей использует отдельный системный
чат и собственный поток событий.

### 2.1. Центральная колонка и граф

В центральной колонке должен быть граф Улья:

- Королева Ева отображается в центре и выделена значком/графическим элементом
  **короны**;
- вокруг неё появляются только ограниченные узлы активных агентов;
- при отсутствии работающих агентов граф не должен создавать фиктивные узлы.

### 2.2. Пустые департаменты

1. Откройте дашборд при отсутствии активных задач и агентов.
2. Проверьте карточки департаментов.
3. Для пустого состояния должно отображаться **«Нет активных агентов»**, а не
   `0/0`. Это означает простой, а не ошибку Core.

### 2.3. Индикатор «Королева печатает»

1. Отправьте из Улья короткое тестовое сообщение и убедитесь, что появился
   индикатор **«Королева печатает»**.
2. Для проверки зависшего задания используйте только безопасную тестовую задачу;
   не прерывайте обновление и не выключайте компьютер.
3. Если terminal-событие не пришло и задача действительно зависла, индикатор
   должен исчезнуть не позднее чем через **60 секунд**.
4. Если индикатор остаётся дольше минуты, зафиксируйте время, ID задачи и
   состояние подключения, затем перейдите к разделу 6.

## 3. Проверка фонового режима (EvaPulse)

### 3.1. Включить проактивное саморазвитие

1. В окне **«Настройки улья»** включите переключатель
   **«Проактивное саморазвитие»**.
2. Убедитесь, что сохранение прошло без ошибки.
3. Проверьте, что одновременно настроены валидный `eva_workspace_path`, основной
   провайдер и положительный дневной бюджет. Одного включённого переключателя
   недостаточно для запуска фоновой задачи.

### 3.2. Добавить тестовую задачу

1. В `TODO.md` тестового `watched_repositories` добавьте отдельную незавершённую
   задачу, например:

   ```markdown
   - [ ] Hive manual test: inspect the sample repository
   ```

   Допустимо добавить её в `docs/development-plan.md` в тестовом checkout.
2. Сохраните файл. Не добавляйте секреты и не просите Еву менять установленный
   клиент.
3. Дождитесь ближайшего пробуждения EvaPulse. Интервал по умолчанию может быть
   до 30 минут; если в тестовой сборке доступна настройка интервала, используйте
   короткое разрешённое значение.

### 3.3. Проверить пробуждение и события

При нормальном пробуждении в `core.jsonl` должна появиться запись:

```text
EvaPulse: all good
```

Если найдена подходящая незавершённая задача, ожидайте вместо этого принятую
задачу Улья и связанные typed-события её создания/выполнения в системном потоке.
В UI отдельно проверьте проекцию статуса EvaPulse: `sleeping`, `unavailable` или
активное состояние должны отражать текущий lifecycle, а не вычисляться по графу.

Если есть зависший worker, EvaPulse сначала создаёт ограниченный recovery-сигнал,
а не дублирует одну и ту же задачу при повторном пробуждении. При срабатывании
rate limit или бюджета нормальным результатом является ожидание до следующего
разрешённого окна, а не бесконечные повторы.

### 3.4. Проверить используемые пути

1. В тестовую задачу поместите различимые, но безопасные пункты: один в
   `watched_repositories`, другой в `eva_workspace_path`.
2. Проверьте в журнале задачи и ответе Евы, что внешний проект был прочитан как
   наблюдаемый, а операции саморазвития выполнялись только в отдельном
   `eva_workspace_path`.
3. Убедитесь, что Ева не открывает `.git`, `target` или `node_modules` как обычные
   каталоги и не изменяет установленный бинарник.

## 4. Проверка бюджета и провайдеров

### 4.1. Лимиты LiteRouter

1. В настройках задайте основной провайдер **LiteRouter** и сохраните его.
2. В секции **«Лимиты запросов и токенов Улья»** задайте тестовые значения RPM,
   RPH и RPD для основного маршрута и сохраните лимиты.
3. На дашборде проверьте карточку бюджета: должны отображаться провайдер
   **LiteRouter** и текущие значения/использование **RPM/RPH/RPD**.
4. Помните: `0` означает «лимит не настроен», а не нулевую доступную ёмкость.

### 4.2. Резервный провайдер Rout

1. Выберите **Rout.my** как резервный провайдер Улья, укажите модель и сохраните
   резервный ключ.
2. Выполните безопасный тестовый запрос через основной маршрут. В обычной работе
   он должен идти через LiteRouter.
3. Для контролируемой проверки исчерпания используйте очень маленький тестовый
   лимит основного маршрута или тестовое окно rate limit. Не создавайте поток
   запросов вручную.
4. После исчерпания LiteRouter проверьте в карточке бюджета сообщение о резерве
   **Rout** и историю/trace последней задачи. Новая задача должна использовать
   изолированный маршрут `hive_fallback`, а не провайдер обычного чата.
5. После проверки верните рабочие лимиты. При 429 EvaPulse может ждать окончания
   cooldown вместо немедленного перехода на резерв — это ожидаемое поведение.

### 4.3. Дневной бюджет `$0.50`

1. В поле **«Дневной лимит бюджета ($)»** укажите `0.50` и нажмите
   **«Сохранить лимит»**.
2. Запишите начальное значение расхода и UTC-время проверки.
3. Выполните только короткие тестовые задачи и наблюдайте карточку бюджета.
4. Убедитесь, что оценка расхода не превышает `$0.50`. После достижения потолка
   EvaPulse не должна создавать новые фоновые задачи до следующих UTC-суток.
5. Не путайте оценку расхода с банковским счётом провайдера: это Core-owned
   защита дневного бюджета Улья.

## 5. Проверка чата

### 5.1. Отправить сообщение с дашборда

1. На дашборде Улья найдите встроенный мини-чат.
2. Введите короткое сообщение, например: `Покажи статус тестового проекта.`
3. Нажмите кнопку отправки и дождитесь ответа. Во время ответа допустим индикатор
   **«Королева печатает»**.

### 5.2. Убедиться в выделенном чате

Проверьте, что сообщение и ответ появились именно в выделенном системном чате
`hive-system-chat`:

- ответ виден в мини-чате Улья;
- активность обычного чата не зажигает индикатор Королевы в Улье;
- в trace/диагностике задача имеет маршрут Улья, а не маршрут обычного чата;
- история обычного чата не содержит это сообщение.

Core назначает маршрут Улья по подтверждённой shell-сессии и идентификатору
`hive-system-chat`; вручную выбирать этот маршрут в обычном чате не нужно.

## 6. Что делать, если что-то не работает

### 6.1. Где искать диагностику

Сначала сохраните время ошибки, текст сообщения UI, ID задачи и выбранные
провайдеры. Затем проверьте:

- **логи Улья** и диагностическую ленту/trace на вкладке «Улей» — состояние
  бюджета, маршрута, задач и approvals;
- `%LOCALAPPDATA%\EvoHime\logs\<YYYY-MM-DD>\core.jsonl` — события Core, EvaPulse,
  задачи, лимиты и `EvaPulse: all good` (имя каталога — текущая дата UTC);
  старые версии писали их в `logs\core.jsonl`;
- `%LOCALAPPDATA%\EvoHime\logs\<YYYY-MM-DD>\supervisor.jsonl` — запуск, остановку
  и восстановление `evohime-core.exe` (старые версии — `logs\supervisor.jsonl`).

Не отправляйте вместе с логами API-ключи. Перед передачей диагностики проверьте,
что в файлах нет секретов и приватного содержимого тестового проекта.

Частые причины:

- **«Нет подключения к Core»** — перезапустите EvoHime и проверьте
  `supervisor.jsonl`;
- путь не сохраняется — проверьте Git checkout, права доступа и отсутствие
  совпадения с установленным продуктом;
- EvaPulse спит — проверьте основной провайдер, API-ключ, бюджет, caps и отдельный
  статус `eva_pulse.status`;
- не находится задача — убедитесь, что это незакрытый Markdown-checkbox (`- [ ]`)
  и что proactive evolution включён;
- не работает резерв — проверьте отдельный резервный ключ, модель и лимиты
  `hive_fallback`.

### 6.2. Откатиться на предыдущую версию

1. Если обновление ещё выполняется, не прерывайте его и не удаляйте каталог
   `%LOCALAPPDATA%\EvoHime`.
2. Закройте EvoHime.
3. Повторно запустите `EvoHime-Setup.exe`: updater использует проверенные staging и
   backup и может восстановить предыдущую рабочую версию при неуспешном
   health-check.
4. Если автоматический rollback не сработал, сохраните логи и обратитесь к
   сопровождающему релиза за предыдущим официальным installer/release. Не заменяйте
   вручную `app.asar`, Core или supervisor и не копируйте бинарники из случайных
   каталогов.
5. После восстановления снова проверьте подключение Core и настройки Улья.
