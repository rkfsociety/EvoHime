# План 04: Постоянное слушание и ambient-память

Обзор плана. Этапы вынесены в отдельные файлы и ревьюятся по одному.

## Цель

Ева может постоянно слушать микрофон, распознаёт речь локально и превращает
услышанное в кандидатов долговременной памяти и в ограниченные проактивные
предложения. Аудио не отправляется наружу и намеренно не сохраняется
приложением на диск. Операционная система теоретически может записать страницы
памяти в pagefile или crash dump; этот остаточный риск снижается
`VirtualLock`, занулением буферов и отключением WER-дампов, но не выдаётся за
абсолютную гарантию. Всё услышанное — кандидат, а не факт: ambient-источник не
может создать активную память без
явного подтверждения пользователя.

## Модель доверия

- Сырой PCM живёт только в памяти процесса `evohime-listener.exe`, по
  возможности в заблокированных страницах, и зануляется при паузе, сбросе
  буферов и завершении высказывания.
- Листенер не имеет доступа ни к SQLite, ни к model gateway, ни к инструментам.
  Он отдаёт Core текст и метаданные и получает политику.
- Core остаётся единственным владельцем policy, памяти и хранилища.
- Речь третьих лиц неотличима от речи пользователя: v1 помечает говорящего
  `unverified` и не позволяет ambient-записи стать активной памятью.
- Проактивность ограничена двумя эффектами: карточка-предложение и
  неисполняемое напоминание. Всё остальное требует клика пользователя и
  проходит обычный approval-путь Core.

## Где живёт конвейер

Отдельный процесс `evohime-listener.exe` под супервизором, клиент отдельного
Core-пайпа с ролью `listener`.

- Сохранение ключа провайдера перезапускает Core: `main.rs` собирает
  `ModelGatewayConfig::from_env()` один раз при старте. Конвейер внутри Core
  закрывал бы микрофон и перезагружал модель при каждой смене ключа.
- `windows_supervisor.rs` уже создаёт Job Object, спавнит ребёнка с
  `kill_on_drop`, следит за heartbeat и держит restart budget.
- Self-update пересобирает продукт на машине пользователя, а `toolchain.ts`
  ставит только Git, Node, Rustup и MSVC Build Tools. CMake не гарантирован,
  поэтому нативные зависимости STT не должны попасть в crate graph Core:
  листенер грузит их как DLL в рантайме.
- Падение инференса не должно ронять агентный цикл и SQLite-транзакции.
- Renderer отвергнут: сырой PCM в Chromium делает инвариант «аудио не на диске»
  недоказуемым (crash dumps, дисковый кэш), а WASM-whisper непригоден по
  скорости.

Core запускает два независимых pipe-сервера в отдельных `tokio::spawn`-задачах:
основной endpoint для shell и `<pipe_name>-listener` для листенера. У каждого
сервера собственный цикл приёма соединений, тот же owner-only DACL и тот же
nonce-handshake; в `ALLOWED_CLIENT_ROLES` добавляется `listener`. Общее
состояние Core синхронизируется через `Arc<Mutex<CoreState>>`, а обработчики не
делят сокеты или последовательную очередь приёма. Контракт листенер↔Core живёт
в отдельном proto (`crates/evohime-listener-ipc`) и не попадает в генерацию Electron.

## IPC и UI

- Additive команды 107–115 в `oneof command`. Теги заняты по 106
  включительно: 92–102 — receipt-команды, 103–105 — plan-review, 106 —
  `ResolveRoutingDecision` из плана 02. События идут через `event_type` +
  JSON-`payload` и не требуют новых сообщений в `oneof event`.
- `npm run generate:protocol` выполняется в том же коммите, что и правка
  `.proto`; сгенерированные файлы не правятся руками.
- Новый вид `listening` («Слух»), индикатор записи в трее и в шапке окна,
  режим capability микрофона в новой панели безопасности (сегодня в renderer
  есть только `PermissionModePicker`, отдельной панели capability нет), бейдж
  «услышано» в очереди памяти `OperationsPanel`.

## Зависимости плана

Блокирующие: нет. План опирается на существующие Memory Extraction,
permissions, desktop IPC, local storage и supervisor; конкретные контракты этих
слоёв перед реализацией сверяются с кодом, а не считаются неизменными.

Подписанные receipts плана 01 уже входят в текущий runtime-контракт EvoHime.
Поэтому проактивный эффект обязан проходить существующий receipt/approval путь
при принятии пользователем; отдельный ambient-receipt не вводится.

## Что план не делает

- Не распознаёт говорящего и не хранит голосовые профили.
- Не отправляет аудио и транскрипты наружу.
- Не даёт ambient-источнику права создавать активную память или запускать
  действия без клика пользователя.
- Не заменяет диалоговый Memory Extraction: тот остаётся на явном триггере.

## Риски

- **whisper.cpp тяжёл.** Лестница отступления: модель `small`→`base`→`tiny` в
  q5_1 → повышение порога VAD и минимальной длины высказывания → смена
  реализации `SpeechEngine` на `Windows.Media.SpeechRecognition` (встроенное
  офлайн-распознавание Windows, без файлов модели) или на `sherpa-onnx`. Трейт
  `SpeechEngine` существует ровно для того, чтобы это была замена конфигурации,
  а не переписывание.
- **Тепловой пакет и батарея.** Листенер меряет RTF; при RTF > 0.5 на пяти
  высказываниях подряд деградирует модель и сообщает об этом в UI.
- **Ложные срабатывания VAD** от музыки и телевизора: дедупликация по хешу и
  минимальная длина отсекают основную массу, остаток виден пользователю в
  списке эпизодов и удаляется одной кнопкой.
- **Речь третьих лиц.** Микрофон в комнате слышит не только владельца.
  Ambient-запись физически не может стать активной памятью без клика, а
  утверждение о третьем лице поднимается до `sensitive`. Это снижает риск, но
  не отменяет его: решение слушать комнату остаётся решением пользователя.
- **Отсутствие DLL или модели** — не ошибка, а состояние `engine_unavailable`.

## Критерии готовности плана

- микрофон не открывается без `microphone_listen = allow`;
- приложение не выполняет файловый I/O для сырого аудио, а тесты проверяют
  отсутствие файлов и отключённые WER-дампы; pagefile не объявляется полностью
  контролируемым приложением;
- любая ambient-запись остаётся `pending_confirmation` при любых входных
  данных;
- пауза, стоп-слово и чёрный список закрывают поток захвата, а не фильтруют
  кадры;
- при неизвестном состоянии UI показывает предупреждение «проверка состояния» и
  никогда не утверждает, что слушание выключено;
- «забыть последние N минут» удаляет транскрипты и отклоняет производных
  кандидатов;
- проактивность не превышает потолок и не выполняет действий без клика;
- CI зелёный без DLL, модели и микрофона.
- ошибка записи в SQLite видна как `storage_failed`/`ambient.storage_error`,
  а не приводит к бесконечному повтору;
- конфликт устройства, сон и пробуждение имеют отдельные проверяемые состояния;
- поставка рантайма и моделей атомарна, проверяет подпись/хеш и не оставляет
  частично установленный набор файлов.
