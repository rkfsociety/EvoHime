# План: самовосстановление и самоулучшение Евы

Дата: 2026-08-12
Статус: черновик, ожидает ревью
Область: `evohime-core` (agent loop), `tool-runtime` (registry, tools), `model-gateway` (retry/routing), `evohime-supervisor` (lifecycle), `evohime-local-storage` (memory)

## 1. Проблема

Агентный цикл Евы (`ToolAgent::run_once_with_cancellation`, [lib.rs:1907](../../crates/evohime-core/src/lib.rs:1907)) сейчас:

- определяет успех инструмента поиском подстрок в человекочитаемом тексте вывода;
- отдаёт одну и ту же recovery-подсказку на любой класс ошибки;
- не накапливает никакого состояния между задачами — каждая задача стартует с нуля;
- не измеряет собственную эффективность, поэтому любое «улучшение» недоказуемо.

Supervisor восстанавливает Core после падения, но бюджет рестартов монотонный и не сбрасывается. Gateway ретраит только запрос до начала SSE.

Цель плана — заменить текстовые эвристики типизированным результатом, довести восстановление до осознанного (классификация → адресная подсказка → эскалация), и замкнуть петлю обучения через уже существующее, но неподключённое хранилище памяти.

## 2. Границы

Не входит в объём:

- vector/RAG-поиск по памяти (остаётся lexical, как задано в `memory_domain`);
- автоматическое изменение Евой собственного исходного кода или промптов без approval;
- перенос состояния из Core в UI;
- смена контракта `desktop-ipc-v1` major-версии.

Инварианты сохраняются: sandbox, таймауты, отмена, approval для опасных инструментов, отсутствие секретов в логах и памяти.

## 3. Фазы

Фазы упорядочены по зависимостям. Фаза 1 — предпосылка для 2 и 3; фазы 4 и 5 независимы и могут идти параллельно.

### Фаза 1. Типизированный результат инструмента

**Задача 1.1. Ввести `ToolOutcome`.**

В [registry.rs](../../crates/tool-runtime/src/registry.rs) добавить:

```rust
pub enum ToolFailureKind {
    NotFound,        // путь/ресурс не существует
    InvalidInput,    // ToolError::InvalidInput, битый JSON аргументов
    Denied,          // PermissionDenied, отклонённый approval
    Timeout,         // ToolError::TimedOut
    NonZeroExit,     // shell.execute с exit_code != 0
    Execution,       // ToolError::Execution и прочее
}

pub struct ToolOutcome {
    pub ok: bool,
    pub kind: Option<ToolFailureKind>,
    pub retryable: bool,
    pub output: String,      // текст для модели
    pub structured: Value,
}
```

Источник истины для `ok` — по убыванию приоритета: (1) вариант `ToolError`; (2) поле `structured` (`exit_code`, `status`); (3) только если оба недоступны — текущая текстовая эвристика, помеченная `#[deprecated]` и логирующая факт fallback в trace.

**Задача 1.2. Нормализовать `structured` у всех инструментов.**

Сейчас `structured` заполняют все 17 обработчиков ([tools/](../../crates/tool-runtime/src/tools/)), но без общего контракта. Ввести обязательное поле `ok: bool` в каждом `structured`, добавить `exit_code` там, где применимо. Покрыть тестом, который итерируется по реестру и проверяет наличие `ok` в успешном ответе каждого инструмента.

**Задача 1.3. Заменить `tool_output_failed` в agent loop.**

[lib.rs:2239](../../crates/evohime-core/src/lib.rs:2239) — вместо `let failed = tool_output_failed(&output)` использовать `outcome.ok`. Ветка approval ([lib.rs:2205](../../crates/evohime-core/src/lib.rs:2205)) должна возвращать `ToolOutcome` с `ok = false, kind = Denied`.

**Исправляемый баг:** строка `"approval denied"` не содержит ни одного маркера из `tool_output_failed`, поэтому отклонённый пользователем вызов сейчас считается успешным и выставляет `mutation_done`. Delivery-gate пропускает задачу без фактической мутации.

**Критерии готовности:**

- регрессионный тест: отклонённый approval для `filesystem.write` не выставляет `mutation_done`;
- тест: `filesystem.read` файла со строкой `error:` внутри даёт `ok = true`;
- тест: `shell.execute` с выводом `test result: ok. 0 failed` даёт `ok = true`;
- тест: `shell.execute` с `exit_code = 1` и пустым stderr даёт `ok = false, kind = NonZeroExit`.

### Фаза 2. Адресное восстановление и эскалация

**Задача 2.1. Таблица подсказок по `ToolFailureKind`.**

Заменить единственную подсказку на [lib.rs:2270](../../crates/evohime-core/src/lib.rs:2270) функцией `recovery_hint(tool_name, kind, structured) -> Option<String>`:

| Kind | Подсказка |
| --- | --- |
| `NotFound` | назвать `filesystem.search` с фрагментом имени; напомнить, что пути workspace-relative |
| `InvalidInput` | вернуть JSON-схему **именно этого** инструмента из реестра, а не общий список примеров |
| `Denied` | объяснить, что повтор не поможет; предложить альтернативу без данного permission или отчёт хозяину |
| `Timeout` | сузить объём (конкретный путь вместо `.`, `--lib` вместо полного прогона) |
| `NonZeroExit` | процитировать первые N строк stderr из `structured`, а не весь вывод |
| `Execution` | общий fallback (текущий текст) |

Схема инструмента берётся из `tool_parameters(name)`, чтобы подсказка не расходилась с реальным контрактом.

**Задача 2.2. Счётчик подряд идущих провалов и эскалация.**

Добавить в цикл `consecutive_failures: HashMap<String, u32>`. Правила:

- успешный вызов инструмента обнуляет его счётчик;
- 2 провала подряд — подсказка усиливается («предыдущий подход не сработал дважды, смени способ»);
- 3 провала подряд — инструмент временно исключается из `specs` на следующие K итераций, Еве сообщается, чем заменить;
- 5 провалов подряд по любым инструментам без единого успеха — остановка с честным отчётом `TaskFailed` вместо молчаливого доедания `max_iterations`.

**Задача 2.3. Починить дедупликацию вызовов.**

[lib.rs:2074](../../crates/evohime-core/src/lib.rs:2074) хеширует сырую строку аргументов, поэтому лишний пробел обходит защиту, а бан действует до конца задачи.

- ключ = `name` + канонизированный JSON (`serde_json::Value` с отсортированными ключами), а не сырая строка;
- вместо вечного бана — счётчик повторов: первый повтор блокируется с подсказкой, но после успешной мутации workspace счётчики чтения (`filesystem.read`, `filesystem.list`, `filesystem.search`) сбрасываются, потому что содержимое файлов изменилось и повторное чтение легитимно.

**Критерии готовности:**

- тест: `{"path":"a"}` и `{"path": "a"}` распознаются как один вызов;
- тест: `filesystem.read` того же пути после успешного `filesystem.patch` не блокируется;
- тест: три подряд `InvalidInput` от одного инструмента исключают его из `specs`;
- тест: пять провалов без успеха завершают задачу событием `TaskFailed` с перечислением классов ошибок.

### Фаза 3. Память в агентном цикле

Хранилище (`MemoryStoreSql::insert/search/list/archive`, [memory_store.rs](../../crates/evohime-local-storage/src/memory_store.rs)) и Core-обёртки ([lib.rs:1208](../../crates/evohime-core/src/lib.rs:1208)) уже есть. Агентный цикл к ним не обращается — это и есть отсутствующая петля обучения.

**Задача 3.1. Pre-task retrieval.**

Перед первой итерацией: lexical-поиск по промпту в scope текущего проекта, top-K (K = 5, bounded по символам) записей класса «урок». Результат вставляется отдельным system-сообщением с явной пометкой, что это прошлый опыт, а не факт о текущем состоянии кода, и что он подлежит проверке.

Пустой результат — не ошибка и не блокирует задачу.

**Задача 3.2. Post-task запись урока.**

После завершения задачи (успех или провал) записать один bounded-урок:

- какой инструмент дал какой класс ошибки и что помогло;
- какая верификационная команда фактически прошла в этом workspace;
- какие пути оказались неверными и какие верными.

Формат урока — детерминированный, собирается Core из накопленной за прогон статистики, **не** свободным текстом от модели: иначе память превращается в канал самовнушения. `MemoryRecord.provenance` = `task:<task_id>`, `privacy` — самый строгий из доступных, TTL — конечный (30 дней), чтобы устаревшие уроки не жили вечно.

**Задача 3.3. Дедупликация и вытеснение.**

Перед вставкой — поиск урока с тем же ключом (инструмент + класс ошибки + нормализованная цель); при совпадении обновляется счётчик подтверждений и `created_at`, новая запись не плодится. Ограничение на число уроков в scope с вытеснением наименее подтверждённых.

**Критерии готовности:**

- тест: два прогона с одинаковым провалом дают одну запись со счётчиком 2, а не две записи;
- тест: retrieval не роняет задачу при пустой или недоступной БД;
- тест: в записанном уроке нет содержимого файлов, токенов и абсолютных путей за пределами workspace;
- ручная проверка: вторая задача того же типа проходит за меньшее число итераций, чем первая (замеряется метриками из фазы 5).

### Фаза 4. Устойчивость процессов и провайдера

**Задача 4.1. Сброс бюджета рестартов supervisor.**

[windows_supervisor.rs:237](../../crates/evohime-supervisor/src/windows_supervisor.rs:237) — `restarts` растёт монотонно за весь срок жизни supervisor. Core, проработавший неделю и упавший в четвёртый раз, больше не поднимется.

- сбрасывать счётчик, если предыдущая генерация прожила дольше порога здорового аптайма (по умолчанию 10 минут, env-override);
- заменить линейный `sleep(250 * restarts)` (максимум 750 мс) на экспоненциальный backoff с jitter и потолком;
- залогировать причину сброса в `supervisor.jsonl`.

**Задача 4.2. Ретрай оборванного стрима.**

[retry.rs](../../crates/model-gateway/src/retry.rs) покрывает только запрос до первого SSE-токена. Обрыв в середине генерации теряет всю итерацию.

- при обрыве до появления tool_call — повтор итерации целиком (идемпотентно, побочных эффектов ещё нет);
- при обрыве после начала tool_call — не повторять, вернуть в цикл как `Execution`-ошибку с подсказкой из фазы 2;
- ограничить число таких повторов на задачу.

**Задача 4.3. Различать классы 429.**

`is_retryable_status` считает все 429 одинаковыми. При троттлинге 190 запросов/час (коммит `467ca1a`) «подожди секунду» и «квота исчерпана» требуют разных решений: первое — backoff, второе — переключение маршрута через `routing_runtime` или честная остановка с сообщением хозяину. Различать по телу ответа/заголовкам провайдера, с безопасным дефолтом «считать исчерпанием» при неоднозначности.

**Критерии готовности:**

- тест: генерация, прожившая дольше порога, обнуляет счётчик рестартов;
- тест: backoff ограничен потолком и не вырождается в ноль;
- тест: обрыв стрима до tool_call приводит к ровно одному повтору;
- тест: 429 с признаком исчерпания квоты не ретраится, а поднимается как ошибка маршрута.

### Фаза 5. Наблюдаемость и измеримость

Без этой фазы улучшения из фаз 1–4 недоказуемы.

**Задача 5.1. Подключить `observability.rs`.**

Модуль ([observability.rs](../../crates/evohime-core/src/observability.rs)) содержит готовый bounded-контракт хуков `BeforeContext / BeforeTool / AfterTool / BeforeCommit / AfterTask` и помечен «намеренно не подключён к `lib.rs`». Это ровно тот шов, куда вешается сбор статистики. Подключить к агентному циклу, сохранив bounded/redacted гарантии контракта.

**Задача 5.2. Метрики прогона.**

Собирать за задачу и писать в БД: число итераций, вызовов по инструментам, успехов/провалов по `ToolFailureKind`, число сработавших recovery-подсказок, факт эскалации, итоговый статус. Эти же данные — источник уроков для фазы 3.

**Задача 5.3. Заменить подстроковые эвристики delivery-gate.**

[lib.rs:2243](../../crates/evohime-core/src/lib.rs:2243) засчитывает верификацию по `arguments.contains("test") || "check" || "build" || "собер"` — `echo "check"` проходит как успешная проверка. Разбирать фактическую команду (первый исполняемый токен + подкоманда) и требовать `exit_code = 0` из `structured`. Порог `research_observations >= 5` заменить на проверку фактического покрытия (был ли прочитан хотя бы один файл, релевантный цели), а не на магическое число.

**Критерии готовности:**

- тест: `echo "check"` не выставляет `verification_test_passed`;
- тест: `cargo test` с ненулевым кодом не выставляет флаг;
- отчёт Core Doctor ([doctor.rs](../../crates/evohime-core/src/doctor.rs)) получает check со сводкой success rate инструментов за последние N задач.

## 5. Риски

- **Память как канал самовнушения.** Урок, записанный со слов модели, может закрепить ошибочный вывод. Смягчение: уроки собирает Core из фактической статистики, TTL конечный, счётчик подтверждений, retrieval помечен как непроверенный опыт.
- **Регрессия delivery-gate.** Ужесточение проверок (5.3) может начать блокировать задачи, которые раньше проходили. Смягчение: сначала логировать расхождение старой и новой оценки, включать строгий режим после сверки на реальных прогонах.
- **Эскалация как новый способ застрять.** Исключение инструмента из `specs` (2.2) может лишить Еву единственного нужного средства. Смягчение: исключение временное (K итераций), никогда не применяется к `filesystem.search` и `filesystem.list`.
- **Рост `lib.rs`.** Файл уже 5097 строк. Новую логику размещать в отдельных модулях (`recovery.rs`, `run_metrics.rs`), а не наращивать `lib.rs`.
